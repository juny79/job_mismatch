# 13 — GraphRAG 일자리 추천 시스템 전환·통합 업그레이드 계획

> 상태: **목표 전환 제안 / 실행 기준안**. 현재 프로젝트는 합성 공고 기반의 로컬 검색·근거 제시 PoC다. 이 문서는 최종 목적을 근거 기반 일자리 추천으로 확장하는 계획이며, 실제 데이터 이용 권한·추천 품질·운영 안전성이 확보됐다는 뜻은 아니다.
> 선행 기준: [08 G0 분석 범위 결정안](08_G0_범위_결정안.md), [09 G2 소량 파일럿 착수안](09_G2_소량_파일럿_착수안.md), [11 웹 UI MVP](11_웹_UI_MVP_실행가이드.md), [12 GraphRAG 기능 구현 계획](12_GraphRAG_기능구현_단계계획.md).

## 1. 목표 전환

프로젝트의 최종 목적을 단순히 지역·직무·기술·복지 조건의 미스매칭을 관찰하는 데서 끝내지 않고, 구직자가 직접 제시한 희망 조건과 검증된 채용공고를 비교해 **조건에 맞는 일자리 후보를 찾아 주고, 추천 이유와 근거를 확인·수정할 수 있게 하는 시스템**으로 확장한다.

추천은 취업 성공, 채용 가능성 또는 개인의 적합성을 보장하는 판정이 아니다. 사용자가 명시한 조건과 현재 확인 가능한 공고 정보 사이의 일치 정도를 순서화하는 의사결정 보조다. 미스매칭 분석은 추천의 대체 목적이 아니라, 승인된 공고 데이터와 별도 승인된 비식별·집계 정보가 있을 때 제공하는 보조 분석 기능으로 둔다.

**제품 목표**
1. 사용자가 지역·직무·기술/경력·급여·고용/근무 조건 등 원하는 조건을 직접 입력한다.
2. 출처·게시일·모집 상태·검수 상태를 확인할 수 있는 공고만 후보로 삼는다.
3. 필수 조건을 먼저 적용하고, 선호 조건의 일치 정도로 후보를 설명 가능한 방식으로 정렬한다.
4. 각 추천에 출처, 게시/확인 시점, 필드 근거, 일치 이유, 미충족·미확인 조건을 표시한다.
5. 적절한 결과가 없거나 근거·최신성이 부족하면 추천하지 않거나 확인 필요로 응답한다.

추천 점수를 합격 가능성·취업 성공 확률로 표현하지 않는다. 공고만으로 청년 전체의 선호나 구인난 원인을 추정하지 않으며, 근거 없는 사실은 생성하지 않는다.

## 2. 현재 기준선과 전환 범위

| 영역 | 현재 상태 | 업그레이드 필요사항 |
| --- | --- | --- |
| 범위·권한 | 부산 실제 근무지·SW/AI·직전 90일 G0 승인. Work24 후보의 출처별 G1은 `pending`; 실데이터 G2 차단 | 추천 목적·사용자·조건 처리 범위를 포함한 G0 보완/재승인, 출처별 저장·검색·추천 표시 권한 확인 |
| 데이터 | 합성 JSONL, 계약 검증, 오류/중복 격리, 검수 상태·품질 요약 | 허가된 필드 매핑, 게시/갱신/마감 및 모집 상태, 필수/우대 구분, 근무·고용 조건, 변경·삭제 반영 |
| 검색·그래프 | 키워드·메모리 그래프·초기 휴리스틱 하이브리드 검색 | 사용자 조건 구조화, 필수 필터, 후보 생성, 조건 비교, 추천 이유와 랭킹 |
| UI·평가 | 로컬 읽기 전용 검색 UI, 합성 질의 평가기·회귀 테스트 | 조건 입력/수정, 매칭 설명·최신성 표시, 추천 정답 세트와 품질 평가 |
| 운영 | 로컬 시연 전용. 인증·권한·TLS·감사·삭제 자동화 미구현 | 개인정보·보안·접근통제·보존/삭제·장애 대응 및 지원 절차 |

현재 구현은 공고 검색·출처 추적·근거 표시의 기반 일부를 제공하지만, **사용자 조건 모델, 추천 점수, 추천 품질 검증 및 실데이터 공고는 아직 구현되지 않았다.** 현재 UI 결과를 개인화 추천이라고 부르지 않는다.

## 3. 추천 기능 계약

### 3.1 사용자 조건

초기 버전은 계정·이력서·장기 프로필을 요구하지 않는 **세션 기반, 비저장 입력**을 권고한다. 지역/통근 범위, 직무, 기술, 경력 수준, 고용 형태, 근무 방식, 급여 하한, 필수 자격, 선호 복지 등을 사용자가 직접 입력하고 각 항목을 `필수`, `선호`, `미입력`으로 지정·수정·초기화할 수 있게 한다.

- 연령·성별·장애·출신·건강·가족 상태 등 민감하거나 보호되는 특성을 추천 변수로 수집·추론하지 않는다. “청년” 자격 확인이 필요한 기능은 필요성·법적 근거가 별도 승인되기 전에는 구현하지 않는다.
- 사용자 기재 경력/기술은 자기기재 정보이며 검증된 능력으로 간주하지 않는다.
- 프로필 저장이나 피드백의 추천 개선 사용은 목적·기간·철회·삭제를 별도 설계하고 동의를 받은 후 검토한다.

### 3.2 후보 생성과 추천 처리

1. **범위 확인:** 질의가 지원 범위인지 확인한다. 조건이 불충분하면 보완을 요청하거나 일반 검색이라고 밝힌다.
2. **필수 조건 필터:** 승인 출처·검수 상태·확인 가능한 모집 상태·명확한 지역/직무 등 적용한다. 필수 조건의 값이 미상이면 일치로 간주하지 않는다.
3. **후보 검색:** 현재 lexical+graph 하이브리드를 초기 후보 검색 기준선으로 사용한다. 동의어·임베딩 검색은 별도 품질·권한 검토 후 추가한다.
4. **조건 비교·랭킹:** 필수 통과와 선호 일치를 분리한다. 필수 조건 실패는 다른 높은 점수로 상쇄하지 않는다. 규칙·가중치는 결정론적이고 버전 관리한다.
5. **근거 검증:** 추천 이유의 각 항목을 승인된 공고 evidence에 연결한다. 근거 부족·충돌은 `미확인` 처리하거나 후보를 제외한다.
6. **결과 표시:** 후보별 일치/불일치/미확인, 점수 구성요소, 출처·게시/확인 시점, 원문 링크, 검색 범위를 표시한다.
7. **Abstain·정정:** 유효 후보가 없거나 최신성을 확인할 수 없으면 추천을 만들지 않는다. 잘못된 공고 신고/숨김을 지원하되 피드백을 무단 학습에 사용하지 않는다.

### 3.3 점수와 표현

추천 v1은 학습 모델이나 LLM 판단이 아닌 **결정론적 조건 매칭**으로 시작한다. 필수 조건 통과 후 선호 조건으로 정렬하고, 점수는 구성 항목과 함께 설명한다. “입력 조건 기준 추천”, “조건 일치도가 높은 공고”로 표현하며 “가장 적합한 직장”, “취업 가능성”, “합격 확률”은 사용하지 않는다. 추천은 취업·채용 결과를 보장하지 않는 의사결정 보조라는 안내를 둔다.

## 4. GraphRAG 역할과 목표 구조

GraphRAG는 추천 자체가 아니다. **그래프/검색은 공고 후보와 관계를 찾고, 결정론적 매칭기는 사용자 조건과 공고 필드를 비교하며, 응답 계층은 근거와 함께 결과를 전달한다.** LLM을 후속 도입하더라도 후보 선택·점수·통계·필수 조건 판단은 코드로 결정한다.

| 계층 | 책임 | 경계 |
| --- | --- | --- |
| 출처·데이터 게이트 | 허용 출처/필드, 게시·갱신·마감, 원천 ID, 검수·버전·삭제 상태 | 출처별 G1 없이 취득·색인·추천 표시 금지 |
| 정규화·품질 | 지역·직무·기술·고용형태·경력·급여 후보와 근거 위치 | 원문/정규화 분리, 미상 보존, 사람 검수 |
| 그래프·검색 | 공고-직무-기술-지역-조건-기업-출처 관계와 lexical/graph 후보 검색 | 관계만으로 사실 주장 금지, 필드 근거 필요 |
| 조건 매칭기 | 필수 조건 필터, 선호 조건 점수, 추천 사유 | 사용자가 입력한 조건만 사용, 규칙 버전 관리 |
| 근거 검증·응답 | 사유와 인용 연결, 최신성 표시, abstain | 근거 없는 주장·점수 보완 금지 |
| UI·평가 | 조건 입력/수정, 비교·정정, 품질·안전 측정 | 최소 데이터, 고지/동의, 접근·삭제 통제 |

현재 `JobPosting`/메모리 그래프에 게시 상태·갱신/마감일, 필수/우대 구분, 고용형태·근무방식·경력/자격, 필드별 evidence 추가를 검토한다. 실제 출처가 제공하고 사용을 허가한 필드만 구현한다. 사용자 프로필을 초기 그래프에 영구 저장하지 않는다.

## 5. 정확성·최신성 요구사항

추천 정확성은 자연스러운 답변보다 **공고의 존재·현재 유효성·조건 사실성·추천 이유의 근거성**으로 정의한다.

| 품질 차원 | 확인 기준 |
| --- | --- |
| 출처 권한 | 수집·저장·정규화·검색·추천 표시·인용·보존/삭제를 출처별 확인 |
| 최신성 | 게시/수정/마감일·확인 시점 및 만료·철회·재게시 처리. 불명확하면 최신이라 단정하지 않음 |
| 사실성 | 추천에 쓰는 근무지·직무·급여·자격 등을 원문 위치·정규화 이력에 연결 |
| 검수 | 핵심 필드의 추출 오류와 표본 검수를 기록. 미승인 값은 분리 또는 제외 |
| 결측 | 미기재·협의·미상·추출 실패·검수 대기를 구분. 임의로 일치/불일치 처리하지 않음 |
| 동기화·삭제 | 원천 수정·삭제·만료를 그래프·검색 인덱스·캐시에 반영하는 절차 설계 |

사용자 조건과 공고의 적합성, 공고 자체가 정확하고 최신인지 두 문제를 분리한다. 모집 상태를 확인하지 못한 공고는 “현재 모집 중인지 확인 필요” 등으로 표시하고 활성 공고라고 단정하지 않는다.

## 6. 평가와 출시 게이트

합성 fixture는 파이프라인·회귀 테스트에만 쓴다. 추천 품질 주장은 승인 데이터와 사람이 검토한 relevance 판단 없이 하지 않는다. 고정 세트에는 직무/기술/지역 조합, 필수 조건, 급여 미기재, 모호한 조건, 만료/무결과/범위 밖 요청, 정보 충돌을 포함한다. 각 질의에 기대 후보, 허용 근거, 필수/선호 판단, abstain 기대를 기록한다.

**지표:** 후보 검색 Recall@k·Precision@k·MRR/nDCG@k; 필수 조건 위반 노출률과 조건별 설명 정확도; evidence coverage·인용 정확도·필드 오류율; 만료/철회 공고 노출률; 미상 정보의 과장 표현률; 무결과·불확실 상황의 abstention 정확도. 사용자 집단별 공정성 분석은 적법하고 동의된 집계 자료가 있을 때만 별도 검토하며 개인 민감정보를 새로 수집하지 않는다.

평가 데이터·질의 버전·지표·임계치·책임자를 결과를 보기 전에 고정한다. 합격 기준은 평가 결과에 맞춰 사후 조정하지 않는다. G2는 소량 기술·품질 확인이며 시장 대표성이나 추천 효과의 증명이 아니다.

| 게이트 | 통과 조건 | 실패 시 |
| --- | --- | --- |
| 추천 범위·정책 | 목적, 대상, 입력 항목, 제외 특성, 데이터·보존 정책 결정 | 개인 추천 구현 보류 |
| 출처별 G1 | 추천 표시까지 포함한 필드별 권한 및 최신성·삭제 조건 확인 | 실데이터 취득/연결 금지 |
| 합성 vertical slice | 조건 입력→필터/랭킹→근거 설명→abstain 테스트 | 추천으로 공개하지 않고 보완 |
| G2 파일럿 | 승인 범위/상한으로 취득, 품질·근거·최신성 확인 | 격리 후 재검토 |
| 오프라인 추천 평가 | 고정 지표 통과, 필수 조건·근거·만료 테스트 | 가중치/범위 재검토 후 새 평가 버전 |
| 사용자 파일럿 | 동의·개인정보·보안·지원과 사용성 검증 | 내부 테스트로 제한 |
| 운영 출시 | 인증·권한·TLS·모니터링·보존/삭제·장애 대응 승인 | 공용 배포 금지 |

## 7. 단계별 통합 실행 계획

### 0단계 — 목적·G0 보완 (다음 우선순위)
- 추천 목적·사용자·입력항목을 기존 G0에 추가할지 프로젝트 책임자가 결정한다.
- 초기 지역(부산 유지 여부), 직무(SW/AI 유지 여부), 제공 채널, 조건 범위, 모집 정보 최신성 기준을 확정한다.
- “정확한 추천”을 공고 유효성·조건 매칭·근거 충실도로 정의하고 미지원 조건을 명시한다.
- 권고안은 계정과 저장 프로필이 없는 비저장 MVP다.
- 출처별 G1 확인에 추천 표시·조건 비교 필드를 포함한다. G0 승인만으로 출처 이용은 허용되지 않는다.

### 1단계 — 합성 데이터 추천 vertical slice
- 사용자 조건 및 추천 결과/evidence 계약을 정의한다.
- 합성 공고에 활성/만료, 필수/우대 등 필요한 사례를 구성한다.
- 결정론적 필수 필터와 선호 점수, 설명 가능한 결과, 무결과 abstain을 UI에 구현한다.
- 조건별 기대 결과 테스트와 평가기를 보완한다. 합성 점수는 기능 회귀에만 사용한다.

### 2단계 — G1 이후 제한 G2·필드 검수
- 공식 API/파일 명세와 권리·이용 조건, 저장/인용/추천 표시/보존/삭제를 확인한다.
- 승인된 필드만 매핑하고 부산/SW·AI/기간·상한(현재 계획 최대 50건 또는 더 낮은 제공자 한도)을 실행 전에 고정한다.
- 실제 근무지, 게시/마감/활성, 필수/우대 조건, 원문 evidence 품질을 검수한다.
- G2 결과 검토 뒤 별도 G3 결정 전에는 수집 확대하지 않는다.

### 3단계 — 추천 오프라인 검증·소규모 사용자 평가
- 승인 자료에 대한 고정 질의와 사람이 검토한 관련 공고 라벨을 만든다.
- 추천 이유가 공고 원문과 일치하는지, 필수 조건 위반/만료 공고/무결과 처리가 정확한지 검증한다.
- 사용자 동의와 비저장 우선 원칙 아래 사용성·조건 수정·신뢰도 안내를 평가한다.
- 결과가 부족하면 운영/개인화 확대 대신 검색·데이터 품질을 개선한다.

### 4단계 — 배포·운영 (별도 승인)
- 계정/프로필 저장은 제품 필요성, 개인정보 검토, 동의/철회/삭제 설계 후에만 추가한다.
- 인증·권한·TLS·비밀 관리·요청 제한·감사/오류 로그·보존/삭제 자동화·백업 정책을 갖춘다.
- 출처 삭제·만료가 검색 인덱스·캐시에 반영되는지 점검하고 운영 책임자를 지정한다.
- 현재 로컬 서버를 인터넷에 직접 공개하지 않는다. Neo4j·벡터 DB·LLM은 데이터 권한·운영 비용·보안 검토 후 필요성이 입증될 때 선택한다.

## 8. 현재 상태와 다음 의사결정

**완료:** 부산/SW·AI/직전 90일 범위에 대한 G0 기록, 프로젝트 내부의 기본 수집·외부 처리 정책, 합성 데이터 검증기·검색/그래프·하이브리드 기준선·읽기 전용 로컬 UI가 마련되어 있다.

**대기/미구현:** 출처별 G1 및 실제 G2 데이터 취득, 추천 목적에 대한 G0 보완, 사용자 조건 입력 모델, 추천 필터·랭커·설명 계약, 실데이터 기준의 관련성 라벨/평가, 운영 보안·개인정보·삭제 체계.

**다음 순서:**
1. 프로젝트 책임자가 추천 중심 목표와 초기 범위(부산/SW·AI 유지 여부), 입력 항목, 비저장 원칙을 결정한다.
2. 이 결정을 반영해 G0 기록 및 출처별 G1 확인 범위를 갱신한다. 출처 권한이 불명확한 동안은 합성 데이터만 사용한다.
3. 합성 데이터 vertical slice와 조건/evidence 회귀 테스트를 구현한다. 이 단계는 추천 동작 검증이지 실사용 추천 품질의 증명이 아니다.
4. 출처별 G1 통과 후 제한 G2 파일럿을 별도로 승인·수행하고, 품질 검토 및 고정 평가를 통과해야 사용자 파일럿을 검토한다.

**진행 게이트:** 이 계획서 작성만으로 기존 G0가 추천 목적까지 자동 확장되거나 출처 이용이 승인되는 것은 아니다. 범위 승인·출처 권한·개인정보/보안 검토를 각각 완료하기 전에는 실데이터 추천 및 공용 서비스 배포를 진행하지 않는다.
