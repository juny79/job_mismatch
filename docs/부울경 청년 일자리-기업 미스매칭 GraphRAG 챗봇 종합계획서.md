## 1. 추진 배경과 목표

부산·울산·경남 기업의 채용 조건과 청년의 역량·근무·정주 선호를 연결해, 양쪽 조건에서 확인되는 차이를 근거와 함께 보여주는 GraphRAG 챗봇을 구축한다. 채용공고의 구조화 정보는 그래프 검색으로 조회하고, 직무·복지 등 서술형 정보는 벡터 검색으로 보완한다. 답변에는 가능한 한 근거가 된 공고·자료의 출처와 표본 범위를 함께 제시한다.

15일 PoC의 목표는 **데이터 확보와 정규화 → 그래프·벡터 검색 → 출처가 있는 답변 생성 → 검증 가능한 데모 구현**까지의 기술적 타당성을 확인하는 것이다. 결과는 제한된 기간과 표본에 기반한 기술 검증으로 해석하며, 부울경 전체 청년의 선호나 기업의 구인난을 대표하는 결과로 확대 해석하지 않는다.

채용공고와 단기 설문에서 관찰된 차이는 미스매칭의 가능성을 살펴보는 단서로 다룬다. 이를 청년 유출의 원인, 취업률 향상 또는 정책 효과의 증거로 표현하지 않는다. 인과관계와 정책 효과 검증은 별도의 후속 실증 과제로 분리한다.

## 2. 15일 PoC 범위와 핵심 산출물

### 2.1 범위 원칙

15일 안에 실제로 수집·정제·검증할 수 있는 데이터와 구현 가능한 기능에 범위를 한정한다. Day 1에 분석 권역 1곳과 직무군 1~2개를 선정하고, 데이터 이용 조건과 수집 가능성을 확인한다. 예시는 창원국가산단의 로봇·제어 직무 또는 부산 센텀권역의 AI·SW 직무다. 예시는 확정된 대상이 아니며, 실제 선정 결과는 착수 시 기록한다. 단일 권역 또는 제한된 직무 표본으로 부울경 전체의 대표성을 주장하지 않는다.

두 번째 권역은 같은 기간·직무군·경력 수준 등 비교 조건을 맞출 수 있고, 이용 가능한 자료가 확보되는 경우에만 추가한다. 비교 조건이 맞지 않으면 권역 간 격차를 수치로 단정하지 않고 기본 범위인 단일 권역 분석을 완료한다.

## 3. 데이터 확보 및 품질 관리

### 3.1 수집 원칙과 후보 출처

수집 전 분석 권역·직무군·대상 기간을 정하고, 해당 범위에 맞는 공고만 포함한다. 공개되어 있다는 이유만으로 재사용이 허용되는 것은 아니므로, 각 출처의 이용약관·라이선스·API 정책·출처 표시 조건을 확인하고 이용 근거를 기록한다. 공식 오픈데이터/API, 지자체·공공기관의 공개 채용정보, 이용 허가를 받은 기업 제공 자료를 우선 검토한다. 민간 채용 사이트 자료는 해당 서비스의 약관과 허용된 수집 방식이 확인된 경우에만 사용한다.

로그인·접근통제 우회, 차단 회피, 과도한 요청, 이용 조건에 반하는 자동 수집은 하지 않는다. 허가 여부나 재배포 조건이 불명확하면 해당 출처는 수집 대상에서 제외하거나 담당 기관에 확인한다. 원문을 외부 LLM·임베딩 서비스로 전송할 필요가 있는 경우에는 해당 데이터의 이용 조건과 전송·보관 정책을 별도로 확인하고, 허용 여부가 불분명하면 로컬 처리 또는 해당 기능 제외를 선택한다.

| 출처 후보 | 수집 방식 | 착수 전 확인 사항 |
| --- | --- | --- |
| 공공기관·공공데이터 포털의 채용 데이터 | 제공 API 또는 내려받기 파일 | 이용 조건, 갱신 주기, 호출 제한, 필드 정의, 출처 표시 방법 |
| 지자체·산단·공공 취업기관 공개 자료 | 공식 제공 파일/API 또는 허가된 수집 | 재이용 범위, 대상 지역·기간, 중복 여부, 원문 링크 유지 조건 |
| 기업이 직접 제공한 공고·채용 자료 | 담당자 전달 또는 협의한 방식 | 제공·분석 동의 범위, 기업명 공개 여부, 보관 기간, 철회·삭제 요청 절차 |
| 민간 채용 플랫폼 자료 | 플랫폼이 명시적으로 허용한 API·다운로드 등 | 약관 및 라이선스, 자동화 허용 여부, 저장·표시·재배포 제한 |

### 3.2 출처 대장과 데이터 보관

자료별로 출처 대장을 작성해 수집 근거와 분석 범위를 추적할 수 있게 한다. 수집 원문은 접근 권한을 제한한 원본 영역에 보관하고, 정제·추출 결과는 원본과 분리한다. 원본을 변경하지 않고 수집 시점의 스냅샷을 보존하며, 갱신·재수집 시에는 버전과 수집 일시를 별도로 기록한다. 보관·삭제 시점은 출처의 이용 조건과 프로젝트의 보안·개인정보 기준에 맞춰 정한다.

| 기록 항목 | 기록 내용 |
| --- | --- |
| 출처 식별 | 출처명, 제공 기관·서비스, 원문 URL 또는 API 식별자, 담당자(해당 시) |
| 이용 근거 | 라이선스·약관·허가 내역, 확인 일자, 출처 표시 조건, 이용·재배포 제한 |
| 수집 범위 | 대상 권역·직무군·공고 게시 기간, 조회 조건, 수집 일시, 수집 담당자 |
| 수집 방법 | API·파일·허가된 수집 방식, 도구·버전, 수집 작업 버전, 오류·재시도 기록 |
| 관리 정보 | 원본 파일명·해시값, 접근 권한, 보관 위치, 보관·삭제 예정일, 데이터 버전 |

### 3.3 채용공고 데이터 구조와 정규화

원문 값과 정규화 값을 함께 보존한다. 표준화 과정에서 원문을 덮어쓰지 않으며, 값의 출처와 변환 규칙을 추적할 수 있도록 한다. 그래프 적재용 식별자는 내부에서 생성하되, 원천 공고 식별자와 연결해 중복·갱신 여부를 확인한다.

| 필드 그룹 | 권장 필드 | 처리 원칙 |
| --- | --- | --- |
| 식별·출처 | 내부 `posting_id`, 원천 공고 ID, 출처 ID, 원문 URL, 수집 시각 | 내부 ID는 안정적으로 부여하고, 출처 정보는 공고별로 보존 |
| 공고 기본정보 | 원문 제목, 정규화 직무군, 경력·고용형태, 게시일·마감일 | 원문과 표준 분류를 분리하고, 확인할 수 없는 값은 추정하지 않음 |
| 기업·산업 | 원문 기업명, 정규화 기업 식별값(가능한 경우), 산업 분류 및 근거 | 동명이인·계열사 혼동에 유의하고 확인 전 기업을 임의 병합하지 않음 |
| 지역 | 원문 근무지, 행정구역 코드(확인 가능한 경우), 권역 매핑 결과·상태 | 기업 본사 주소와 실제 근무지를 구분하고, 산단 소속을 주소만으로 단정하지 않음 |
| 급여·근무조건 | 원문 급여 문구, 최저·최고액, 단위·주기, 급여 협의 여부, 근무형태 | 연봉·월급·시급을 구분하고 단위 환산은 근거와 규칙이 있을 때만 수행 |
| 역량·복지 | 원문 문장, 정규화 스킬·복지 용어, 필수·우대 구분, 근거 문장 | 필수와 우대를 구분하고, 공고에 없는 혜택·요구 역량을 추론해 추가하지 않음 |
| 품질·추출 | 원문 필드, 정규화 필드, 추출 방법·모델 버전, 검수 상태·수정 이력 | 자동 추출값은 원문 근거와 연결하고, 검수 전 값은 검증 완료로 표시하지 않음 |

결측은 `0`, 임의 평균, 고정 급여 등으로 대체하지 않는다. 최소한 **공고에 미기재**, **해당 없음**, **자료 형식상 확인 불가**, **추출 실패**, **검수 대기**를 구분해 기록한다. 급여는 원문에 범위가 있으면 최저·최고액을 별도로 저장하고, `협의`, `회사 내규`, 시급·월급 등 연봉 환산 근거가 없는 표현은 확인되지 않은 금액으로 유지한다. 복지와 스킬도 명시 여부와 추출 여부를 구분한다.

스킬·직무·복지 용어 사전을 만들어 동의어와 표기 변형을 정규화한다. 예를 들어 한글·영문 표기가 다르더라도 동일 개념으로 확인된 경우에만 표준 용어에 연결한다. 자동 유사도 매칭은 후보 제안으로 취급하며, 승인되지 않은 유사어를 자동으로 병합하지 않는다. 공고의 필수 요건과 우대 사항, 공고 사실과 모델의 추론을 데이터 구조에서도 구분한다.

### 3.4 수집·정제 파이프라인

1. **범위 확정:** 권역·직무군·대상 기간과 필수 필드를 정하고, 출처별 이용 조건을 확인한다.
2. **원본 적재:** 허용된 방식으로 수집한 원문을 변경 없이 보관하고 출처 ID·수집 시각을 부여한다.
3. **형식 검증:** 필수 키, 인코딩, 날짜·금액 형식, 파일 손상 여부 및 스키마 변화를 점검한다.
4. **중복·갱신 처리:** 출처 공고 ID를 우선 비교하고, ID가 없는 경우 제목·기업·근무지·게시일 등 복합 기준으로 후보를 찾아 수동 확인한다. 재게시·수정 공고는 동일 공고로 무조건 합치지 않고 버전 또는 별도 게시물 여부를 기록한다.
5. **정규화·추출:** 지역·직무·스킬·복지·급여를 원문과 분리해 정규화한다. LLM을 사용하는 경우 구조화 출력의 형식 검증과 원문 근거 대조를 수행한다.
6. **검수·격리:** 검수 상태를 표시하고, 출처 불명·범위 밖·파싱 오류·이용 조건 불명 자료는 분석용 데이터에서 격리한다.
7. **분석용 내보내기:** 검수된 버전만 그래프·벡터 저장소에 적재하고, 제외·결측·변환 건수를 품질 보고서에 남긴다.

### 3.5 품질 점검과 통과 기준

품질 수치는 실제 수집 결과가 아닌 **PoC 운영 기준 제안**이다. Day 2에 출처별 스키마와 수집 여건을 확인한 뒤 확정하며, 기준을 충족하지 못한 필드는 분석 범위를 축소하거나 결과에 사용할 수 없다고 명시한다.

| 점검 항목 | 방법 및 제안 기준 | 미충족 시 처리 |
| --- | --- | --- |
| 이용 근거·출처 추적 | 분석에 사용하는 모든 레코드에 출처 식별자와 수집 시각 기록. 이용 가능 여부 확인 전 적재 금지 | 미확인 자료 격리 또는 제외 |
| 범위 적합성 | 권역·직무군·게시 기간을 레코드별로 확인하고 범위 밖 자료 표시 | 분석 대상에서 제외하고 제외 사유 집계 |
| 필수 정보 | 공고 제목, 출처, 원문 근거 위치를 확인. 기업명·지역 등은 공고에 있는 경우에만 채움 | 누락 상태를 기록하고 해당 항목 분석에서 제외 |
| 중복·버전 | 자동 중복 후보 탐지 후 중복·재게시·수정 공고를 구분해 검수 | 불확실한 후보는 자동 병합하지 않고 검수 대기 |
| 날짜·급여 유효성 | 날짜 순서, 금액의 양수 여부, 급여 단위·주기와 환산 근거 점검 | 오류 수정 근거를 남기거나 결측·검수 대기로 전환 |
| 자동 추출 정확도 | 출처·직무군별 층화 표본을 사람이 원문과 대조. 권장 표본은 전체의 약 10%(최소 30건, 최대 50건) | 핵심 필드 오류가 반복되면 프롬프트·규칙 수정 후 재검수하거나 해당 필드 제외 |
| 결측·제외 보고 | 핵심 필드별 분모를 명시해 결측률을 산출하고 제외 사유별 건수를 공개 | 결측이 큰 항목은 집계·비교를 보류하거나 제한적으로 해석 |

추출 정확도는 표본 검수 결과와 산식을 함께 보고한다. 금액·지역·필수/우대처럼 분석에 영향이 큰 필드는 원문 근거와 일치하는지 별도로 확인하고, 검수 표본에서 신뢰할 수 없는 항목은 전체 데이터에 정확한 값인 것처럼 적용하지 않는다. 표본 검수만으로 전체 레코드가 정확하다고 단정하지 않는다.

### 3.6 단계별 데이터 산출물

- **Day 1:** 출처 후보·이용 조건 대장, 권역·직무군·대상 기간 결정 기록, 데이터 필드 초안.
- **Day 2:** 소량 파일럿 수집 결과, 출처별 확보 가능 건수와 결측·중복 예비 점검, 500건 목표 유지 또는 범위 조정 결정.
- **Day 3~4:** 원본·정제 데이터 버전, 정규화 사전, 자동 추출 및 검수 결과, 품질 보고서 초안.
- **그래프 적재 전:** 이용 가능 여부, 출처 연결, 필수 필드·결측 상태, 중복 검수 상태를 확인한 적재 승인 목록.

위 일정은 계획 기준이며 실제 수집량이나 품질 결과를 미리 보장하지 않는다. 최종 보고에는 수집 건수뿐 아니라 제외 건수, 출처별 구성, 중복·결측·검수 결과와 남은 한계를 함께 기재한다.

## 4. 청년 선호 조사 및 미스매칭 분석

### 4.1 조사 목적과 해석 범위

청년 조사는 선정된 권역·직무군과 관련된 구직자의 역량, 희망 직무, 근무·보상·정주 조건의 선호를 탐색하기 위한 자료로 수집한다. 채용공고의 요구조건과 비교해 어떤 항목에서 차이가 관찰되는지 확인하고, 후속 인터뷰·실증에서 검증할 질문을 도출한다. 단기 온라인 설문은 자발적 응답에 따른 편의 표본이므로 모집단의 선호 비율이나 부울경 전체 청년의 의견으로 일반화하지 않는다.

조사 결과로 청년이 특정 지역을 기피하는 이유, 실제 지원·이직 행동 또는 청년 유출의 원인을 단정하지 않는다. 공고상 조건과 응답자의 선호가 다르다는 사실은 가능한 조건 차이를 나타낼 뿐이며, 채용 성과·기업의 구인난·정책 효과를 입증하지 않는다. 조사 시행 전 목적, 대상 기준, 질문지 버전, 모집 경로, 실시 기간을 기록하고 개인정보·동의 절차는 6장에서 정한 기준에 따른다.

### 4.2 조사 대상과 모집

| 항목 | 계획 기준 |
| --- | --- |
| 대상 | 착수 시 합의한 청년 연령·자격 기준을 충족하고, 선정 권역·직무군과 관련된 취업·구직·직무교육 경험 또는 관심이 있는 응답자 |
| 모집 방식 | 대학·취업지원기관·청년기관·직무 커뮤니티 등 협조 가능한 경로를 이용하되, 경로별 모집 인원과 모집 기간을 기록 |
| 목표 | 유효 응답 30~50명. 이는 PoC 운영 목표이며 통계적 대표 표본을 의미하지 않음 |
| 유효 응답 판정 | 참여 동의와 대상 기준을 확인하고, 핵심 문항의 응답 가능 여부·중복 응답·응답 품질을 사전에 정한 규칙으로 확인 |
| 선택 인터뷰 | 5~8명 목표. 별도 참여 의사를 받은 뒤 진행하며, 설문 응답과 인터뷰 참여 정보의 연결 여부는 동의 범위에 따름 |

청년의 정의와 연령 범위는 적용할 사업·기관 기준을 확인해 조사 전에 명시하고, 임의로 여러 기준을 혼용하지 않는다. 응답자 모집은 성별·연령·재학·재직·구직 상태 등 일부 집단에 편중될 수 있으므로 모집 경로와 응답자 특성을 요약해 공개한다. 특정 하위집단의 표본 수가 적으면 별도 비율·비교 결과를 제시하지 않고 통합하거나 분석을 생략한다.

### 4.3 설문 구성안

설문은 응답 시간을 줄이기 위해 핵심 항목 중심으로 구성한다. 구체 문항은 파일럿 응답을 통해 이해 가능성과 소요 시간을 점검한 뒤 확정한다. 급여·근무지 등 응답이 곤란한 항목에는 **응답하고 싶지 않음**, **잘 모르겠음**, **해당 없음** 선택지를 제공하고, 주관식 문항은 선택 응답으로 둔다.

| 문항 영역 | 수집 내용 예시 | 설계 원칙 |
| --- | --- | --- |
| 적격성·상태 | 조사 대상 기준 해당 여부, 재학·재직·구직 등 현재 상태 | 분석에 필요한 범위만 묻고, 세부 개인 이력은 불필요하게 수집하지 않음 |
| 희망 직무·산업 | 희망 직무군, 관심 산업, 근무 희망 권역 | 미리 정의한 선택지와 기타 응답을 함께 제공하고 복수 선택 여부를 명시 |
| 보유 역량 | 관련 기술·직무 역량의 보유 여부와 자기평가 수준, 학습 의향 | 보유·교육 경험·숙련도를 분리하고 자기보고 값임을 표시 |
| 근무 조건 | 출근·하이브리드·원격 선호, 근무시간·유연성, 통근 가능 시간 범위 | 정확한 집 주소나 개인 위치정보를 묻지 않고 구간으로 응답받음 |
| 보상 조건 | 희망 급여 범위와 급여 단위·기간, 협의 가능 여부 | 세전·세후 등 기준을 질문에 명시하고 무응답 선택지를 제공 |
| 복지·정주 조건 | 통근 지원, 주거 지원, 교육, 유연근무 등 중요도 | 중요도 척도와 반드시 필요한 조건을 구분하고, 모든 항목을 필수 조건으로 간주하지 않음 |
| 판단 근거·장벽 | 지원을 검토할 때 중요하게 보는 요소, 추가로 필요한 정보 | 유도 질문을 피하고 선택형 중심으로 구성, 자유 서술은 선택으로 운영 |

선호도 척도는 문항 간 같은 방향으로 통일한다. 예를 들어 5점 척도를 쓸 경우 양끝의 의미와 중간값을 설명하고, 무응답·모름을 척도 점수에 포함하지 않는다. 순위형 응답은 응답자에게 우선순위 선택 개수를 알려주며, 순위 점수와 중요도 점수를 혼합해 하나의 지표처럼 해석하지 않는다.

### 4.4 파일럿·응답 정제

본 조사 전에 소수의 파일럿 응답(계획상 3~5명)을 받아 문항의 용어 이해도, 선택지 누락, 응답 시간, 모바일 화면 사용성을 확인한다. 파일럿 결과를 바탕으로 수정한 경우 질문지 버전을 갱신하고, 파일럿 응답을 본 분석에 포함할지는 문항 변경 여부와 응답자 동의·자료 호환성을 확인해 결정한다.

응답 데이터는 다음 기준으로 정리한다.

1. 동의 및 대상 기준을 확인하고, 동의하지 않았거나 대상이 아닌 응답은 분석 자료에서 제외한다.
2. 중복 가능성은 개인정보를 과도하게 수집하지 않는 방식으로 점검하며, 판단 근거가 불충분하면 임의로 삭제하지 않고 검토 대상으로 남긴다.
3. 핵심 문항의 무응답·모름·해당 없음은 각각 구분해 저장하고, 분석 분모에서 제외한 이유를 기록한다.
4. 비현실적 입력, 동일 응답 반복 등 품질 점검 규칙은 사전에 정하고, 자동 탐지 결과만으로 응답을 제거하지 않는다.
5. 자유 서술에 개인정보·기업 비밀 등 민감 내용이 포함되면 목적에 필요한 범위에서 비식별화하고, 공개 리포트에는 원문을 그대로 인용하지 않는다.

### 4.5 채용공고와 선호 자료의 비교 방법

비교 전 공고와 설문 자료의 권역·직무군·경력 수준·대상 기간·범주 정의가 얼마나 맞는지 확인한다. 일치하지 않는 범주를 억지로 대응시키지 않고, 비교 가능한 항목과 불가능한 항목을 구분한다. 공고의 요구 스킬은 **필수**와 **우대**를 나누고, 설문에서 확인한 역량은 자기보고 값으로 표시한다. 공고에 나온 요구조건과 응답자의 역량을 같은 객관적 능력 측정값처럼 취급하지 않는다.

| 비교 항목 | 분석 방법 | 해석 시 주의점 |
| --- | --- | --- |
| 직무·스킬 | 비교 가능한 표준 분류로 매핑한 뒤 공고에서 요구된 비율과 응답자가 보유·학습 의향을 표시한 비율을 병렬 제시 | 자기평가와 공고 요건의 측정 방식이 다르므로 능력 부족이나 원인으로 단정하지 않음 |
| 급여 | 단위·기간·경력 조건이 비교 가능한 명시 급여 공고만 사용하고, 응답자의 희망 범위와 공고 급여 범위의 겹침 여부 또는 구간별 분포를 제시 | 급여 미기재·협의·단위 불명 값은 임의 환산하지 않으며, 포함·제외 건수와 비교 기준을 표시 |
| 근무·정주 조건 | 원격·유연근무·통근·주거 등 공고에 명시된 제공 여부와 설문 중요도·선호도를 항목별 병렬 비교 | 공고에 미기재된 것을 기업이 제공하지 않는다고 해석하지 않음. 명시 여부와 실제 제공 여부를 구분 |
| 지역·직무 선택 | 조사 응답에서 선택된 희망 범위와 공고의 근무지·직무 분포를 기술적으로 비교 | 모집 경로와 표본 편중, 공고 수집 범위의 영향을 함께 설명 |

분석 지표는 각 항목별 유효 분모를 명시한다. 예를 들어 스킬 요구 비율의 분모는 해당 직무군에서 스킬 정보를 확인할 수 있는 공고 수로, 선호 비율의 분모는 해당 문항에 유효 응답한 인원으로 구분한다. 두 비율의 차이를 산출하는 경우에도 분모가 다른 탐색적 비교임을 표시하고, 단일한 ‘미스매칭 점수’로 합산하지 않는다. 급여 평균이나 격차를 제시할 때는 표본 수, 급여 단위, 기간, 경력·직무 비교 조건, 산식 및 결측 제외 기준을 함께 공개한다.

### 4.6 인터뷰와 정성 분석

선택 인터뷰는 설문으로 설명하기 어려운 선택 이유와 조건의 우선순위를 탐색하는 보완 자료로 활용한다. 질문은 “왜 특정 지역을 떠나는가”처럼 원인을 전제하지 않고, “어떤 조건을 중요하게 고려했는가”, “공고에서 확인하기 어려웠던 정보는 무엇인가”와 같이 경험·판단을 개방형으로 묻는다. 면담 기록은 주제별로 요약·코딩하고, 가능하면 두 명이 일부 기록을 교차 검토해 해석 차이를 확인한다. 인터뷰 인용은 별도 동의가 있고 재식별 위험이 낮은 경우에만 사용하며, 소수 사례를 전체 청년의 의견으로 일반화하지 않는다.

### 4.7 결과 제시와 해석 제한

진단 결과에는 다음 항목을 함께 표시한다.

- 조사·공고의 대상 권역, 직무군, 수집·조사 기간과 모집 경로
- 공고 수, 유효 응답자 수, 인터뷰 수 및 항목별 유효 분모
- 공고의 명시 조건과 미기재 조건, 응답자의 무응답·모름 처리 방식
- 표준화·비교 규칙, 급여 환산 여부와 제외 기준
- 표본 편중, 자기보고 측정, 공고 정보의 시점 차이 등 해석상 한계

표본이 작은 하위집단은 개인이나 소수 응답자를 알아볼 수 있는 조합으로 공개하지 않는다. 계획상 집계표에서 셀의 응답자가 5명 미만인 경우에는 해당 값을 공개하지 않거나 더 큰 범주로 합치는 기준을 적용한다. 이는 공개 단계의 최소 보호 기준이며, 구체적인 비식별·접근통제·보관 기준은 6장에서 정한다.

결과 문구는 “이번 표본에서 해당 조건을 중요하다고 응답한 비율이 높게 관찰됐다”처럼 범위와 근거를 한정한다. “급여가 낮아 청년이 유출된다”, “복지를 개선하면 취업률이 오른다”와 같은 인과 표현이나 효과 예측은 PoC 결과로 제시하지 않는다. 조사 결과는 후속 조사·실증의 가설과 질문을 만드는 데 활용한다.

## 5. GraphRAG 아키텍처와 그래프 설계

### 5.1 설계 원칙

본 PoC에서 GraphRAG는 지식그래프 자체가 결론을 내리는 시스템이 아니라, 채용공고의 구조화된 조건과 서술형 근거를 함께 찾아 답변의 근거로 제공하는 검색·설명 구조로 사용한다. 급여·건수·비율 같은 집계는 검증 가능한 데이터 쿼리와 애플리케이션 로직으로 계산하고, LLM은 검색 결과의 요약·설명만 수행한다. 검색되지 않은 사실이나 공고에 명시되지 않은 조건은 추측하지 않고 미확인으로 표시한다.

데이터 모델은 3장의 원본·정규화 분리 원칙을 따르고, 4장의 설문은 개인별 응답을 그래프에 적재하지 않는다. 설문 결과를 사용할 경우 동의 범위 내에서 비식별 집계값만 별도 데이터 영역으로 관리하며, 집계 정의·분모·조사 기간을 함께 저장한다. 공고 요구조건과 청년 선호 집계는 서로 다른 출처와 측정 방식임을 유지한다.

### 5.2 논리 아키텍처

| 계층 | 구성 요소 | 책임 |
| --- | --- | --- |
| 사용자 인터페이스 | Streamlit 검색·질의·결과 화면 | 질문 입력, 필터 선택, 답변·근거·표본 한계 표시, 데모 그래프 시각화 |
| 질의 처리 | 입력 검증, 의도 분류, 검색 경로 선택 | 공고 검색·집계·비교·설명 요청을 구분하고 허용된 검색 작업으로 전달 |
| 그래프 검색 | Neo4j 읽기 전용 조회 | 기업·공고·직무·지역·스킬·복지 관계 및 구조화된 집계 조회 |
| 벡터 검색 | ChromaDB 또는 이에 준하는 로컬 벡터 저장소 | 공고의 직무·자격·복지 서술에서 질문과 관련된 원문 근거 검색 |
| 근거 결합·계산 | 결과 정규화 및 결정론적 집계 | 그래프 결과와 벡터 근거를 출처 ID로 연결하고, 수치·분모·결측 처리를 명시 |
| 답변 생성 | LLM 또는 지정 언어모델 | 검색된 근거만 사용해 요약, 미확인 정보·범위·한계 및 인용 표시 |
| 데이터·운영 | 정제 파일, Neo4j, 벡터 인덱스, 설정·로그 | 접근통제, 버전 관리, 오류 추적, 재현 가능한 적재·색인 관리 |

기본 실행 경로는 **질문 입력 → 입력·범위 확인 → 질의 유형별 검색 → 근거 연결 및 수치 계산 → 근거 기반 답변 → 출처·표본 한계 표시**로 한다. 그래프와 벡터 검색 중 하나가 실패하거나 결과가 없으면 성공한 것처럼 답변하지 않고, 부분 결과 또는 검색 실패를 사용자에게 알린다.

### 5.3 그래프 모델

핵심은 `JobPosting`(채용공고)을 기업·지역·직무와 요구 역량·제공 조건 사이의 연결점으로 두는 것이다. 모든 관계와 속성은 실제 확보 가능한 데이터만 적재한다. `IndustrialComplex`는 공식 자료 또는 검증 가능한 주소 매핑으로 소속이 확인될 때만 연결하며, 단순히 행정구역이 같다는 이유로 특정 산단 소속을 부여하지 않는다.

| 노드 | 주요 속성 예시 | 설계 메모 |
| --- | --- | --- |
| `JobPosting` | 내부 공고 ID, 원천 ID, 제목, 게시·마감일, 경력, 고용형태, 급여 원문·단위·범위, 출처 ID, 원문 URL, 검수 상태 | 공고 사실의 핵심 단위. 수집 시점·버전을 보존하고 결측 상태를 구분 |
| `Company` | 내부 기업 ID, 확인된 기업명, 기업 식별 근거 | 이름만으로 동일 기업을 병합하지 않음. 불확실한 연결은 보류 |
| `Role` | 표준 직무 코드·명칭, 분류 버전 | 원문 직무명과 표준 직무군을 분리 |
| `Skill` | 표준 용어, 동의어, 유형, 사전 버전 | 자동 유사도는 후보 제안으로만 사용하고 승인된 매핑을 적재 |
| `Benefit` | 표준 복지·근무조건 용어, 동의어 | 공고에 명시된 조건만 연결하고 미기재와 미제공을 구분 |
| `Location` | 원문 근무지, 행정구역 코드, 매핑 상태 | 근무지와 본사 주소를 구별하고 위치 정확도를 기록 |
| `IndustrialComplex` | 확인된 권역·산단 ID, 명칭, 출처 | 공식 경계·자료 등 확인 가능한 근거가 있을 때만 사용 |
| `Industry` | 산업 분류 코드·명칭, 분류 버전 | 확인된 산업 분류만 저장하고 모델 추론은 별도 검수 |
| `Source` | 출처 ID, 기관·서비스, 수집일, 이용 조건 참조 | 각 공고의 출처와 갱신 이력을 추적 |
| `PreferenceAggregate` | 지표, 값·범주, 분모, 기간, 조사 버전, 세그먼트 기준 | 개인 응답이 아닌 승인된 집계값만 저장. 소수 집단 재식별 위험 점검 |

| 관계 | 방향 | 의미·조건 |
| --- | --- | --- |
| `(:Company)-[:POSTED_JOB]->(:JobPosting)` | 기업 → 공고 | 출처·공고에서 확인된 기업 연결 |
| `(:JobPosting)-[:HAS_ROLE]->(:Role)` | 공고 → 직무 | 원문 직무명과 정규화 분류의 연결 |
| `(:JobPosting)-[:REQUIRES_SKILL {requirement_type, evidence}]->(:Skill)` | 공고 → 역량 | 필수·우대 구분 및 원문 근거 보존 |
| `(:JobPosting)-[:OFFERS_BENEFIT {evidence}]->(:Benefit)` | 공고 → 조건 | 명시된 복지·근무 조건. 미기재는 관계 부재만으로 제공 안 함을 뜻하지 않음 |
| `(:Company)-[:LOCATED_AT]->(:Location)` | 기업 → 위치 | 이 관계가 실제 근무지를 나타내는지 속성·정의로 구분 |
| `(:Location)-[:WITHIN]->(:IndustrialComplex)` | 위치 → 권역 | 확인 근거가 있는 경우에만 연결 |
| `(:Company)-[:IN_INDUSTRY]->(:Industry)` | 기업 → 산업 | 분류 근거와 분류 체계 버전 관리 |
| `(:JobPosting)-[:FROM_SOURCE]->(:Source)` | 공고 → 출처 | 원천 자료와 이용 조건 추적 |
| `(:PreferenceAggregate)-[:ABOUT_ROLE]->(:Role)` | 집계 → 직무 | 해당 집계의 분류 기준을 명확히 표시 |

관계 속성은 반드시 필요한 근거·구분 정보만 포함한다. 그래프에 적재된 사실은 공고 원문 또는 확인된 출처로 역추적 가능해야 한다. 내부 식별자와 원천 ID를 구분하고, `Company.name`처럼 충돌할 수 있는 표시명을 유일 키로 간주하지 않는다. 제약조건·인덱스는 실제 DB 버전과 스키마에 맞춰 설계하며, 공고의 원천 ID는 출처 ID와 결합해 중복 충돌을 줄인다.

### 5.4 그래프·벡터 저장소 분리와 데이터 연결

그래프 저장소에는 필터·관계 탐색·정확한 집계에 필요한 정규화 필드와 출처 식별자를 저장한다. 벡터 저장소에는 허용된 범위의 공고 서술 텍스트를 적절한 단위로 분할해 저장하고, 각 청크에 `posting_id`, `source_id`, 원문 URL 또는 위치, 게시 시점, 텍스트 유형, 데이터 버전을 메타데이터로 붙인다. 개인 식별 정보, 불필요한 연락처, 출처 이용 조건상 전송이 허용되지 않은 텍스트는 임베딩 대상에서 제외한다.

| 데이터 유형 | 우선 저장 위치 | 연결 키·관리 방법 |
| --- | --- | --- |
| 공고 ID·지역·직무·급여 등 구조화 필드 | Neo4j | 안정적인 `posting_id`, 출처 ID, 게시 버전 |
| 공고 자격·업무·복지 원문 구절 | 벡터 저장소 및 허가된 원문 보관소 | 청크별 공고 ID·출처 ID·원문 위치·버전 |
| 기업·스킬·복지·직무 관계 | Neo4j | 검수된 정규화 ID와 원문 근거 연결 |
| 청년 조사 집계 | 접근 범위를 분리한 집계 데이터 또는 허가된 그래프 노드 | 조사 버전·기간·분모·범주 정의, 개인별 응답은 제외 |
| 출처·수집·이용 메타데이터 | Neo4j 및 출처 대장 | 출처 ID로 연결, 라이선스·허가 정보 자체는 별도 대장 참조 가능 |

그래프와 벡터 저장소의 적재는 동일한 정제 데이터 버전을 기준으로 수행한다. 재적재 시 기존 인덱스를 무조건 덧붙이지 않고 버전별 재생성 또는 멱등 적재를 적용해 오래된 공고·청크가 검색에 남지 않도록 한다. 공고의 수정·삭제가 확인되면 연결된 그래프 레코드와 벡터 청크가 함께 갱신·제외되는 절차를 둔다.

### 5.5 질의 처리와 근거 기반 답변

1. **질문 분류:** 공고 검색, 조건 집계, 비교, 서술 근거 검색 등으로 분류하고, 선정 권역·직무·기간 밖의 질문은 범위 제한을 알린다.
2. **허용 검색 계획:** 집계·필터 질문은 사전 정의한 매개변수형 Cypher 템플릿을 우선 사용한다. 텍스트 의미 검색은 벡터 검색을 수행하고, 필요한 경우 그래프 관계로 후보 범위를 좁힌다.
3. **검색·검증:** 조회 결과에 출처 ID·게시 시점·검수 상태가 있는지 확인하고, 벡터 청크의 인용 위치가 원문과 연결되는지 검증한다.
4. **계산:** 건수·비율·급여 통계는 애플리케이션 로직 또는 검증된 집계 쿼리에서 계산한다. 분모·단위·결측 제외 규칙을 결과와 함께 전달한다.
5. **근거 패키징:** 답변 생성에 사용할 검색 결과, 출처, 표본 범위, 불확실성, 미확인 항목을 하나의 구조화된 근거 묶음으로 전달한다.
6. **응답 생성:** LLM은 근거 묶음에 없는 사실을 추가하지 않으며, 출처가 없거나 결과가 불충분하면 답변을 보류하거나 제한적으로 응답한다.
7. **화면 표시:** 답변과 함께 근거 공고·출처, 게시일, 표본 수·기간, 결측·한계 및 가능한 경우 관련 검색 조건을 제공한다.

Text2Cypher를 데모에 포함하더라도 임의의 사용자 질의를 운영 DB에 직접 실행하지 않는다. 읽기 전용 DB 계정, 허용 라벨·관계·속성 목록, 읽기 쿼리 제한, 결과 행 수·실행 시간 제한, 쿼리 구문 검증을 적용한다. `CREATE`, `MERGE`, `DELETE`, `SET`, 스키마 변경 등 쓰기·관리 작업은 차단한다. 생성 쿼리가 검증을 통과하지 못하거나 쿼리 결과가 범위를 벗어나면 템플릿 검색으로 대체하거나 오류를 표시한다. 사용자 입력과 공고 원문은 신뢰할 수 없는 텍스트로 취급해 프롬프트 인젝션 지시가 검색·권한 정책을 바꾸지 못하도록 한다.

### 5.6 색인·검색 운영 기준

그래프에는 공고 ID, 출처 ID, 직무·지역·기간 등 실제 필터에 사용하는 속성의 제약조건·인덱스를 검토한다. 벡터 인덱스의 임베딩 모델, 청크 크기·겹침, 유사도 기준은 실제 한국어 공고 소량 샘플로 비교해 정하며, 선택한 모델·버전·설정을 기록한다. 수집 데이터가 작으므로 복잡한 랭킹 학습보다 출처 정확성, 검색 재현성, 응답 추적성을 우선한다.

검색 결과에는 최소한 내부 공고 ID와 출처 참조가 유지되어야 한다. 서로 다른 출처의 동일 공고가 후보로 검색되면 중복 정책에 따라 중복 여부를 표시하고 집계에서 이중 계산하지 않는다. 데모 전 주요 질문 유형별 테스트 질의와 기대 근거를 준비하고, 빈 결과·저신뢰 결과·DB 연결 실패·LLM 실패 시 안전한 오류 화면을 확인한다.

### 5.7 권장 PoC 구성과 결정 보류 항목

기준 원문의 후보를 반영한 최소 구성은 **Python 적재·질의 모듈, Neo4j 그래프 DB, 로컬 ChromaDB 벡터 저장소, Streamlit UI**다. 단, 이는 확정된 기술 선택이 아니라 15일 PoC에서 구현·운영이 가능한지 확인할 기본안이다. Neo4j 클라우드 사용 여부, 외부 LLM·임베딩 사용 여부, 데이터 저장 위치, 사용 프레임워크는 보안·이용 조건·팀 경험·비용을 확인한 뒤 Day 1~2에 확정한다. 해당 조건을 만족하지 못하면 로컬 DB나 템플릿 기반 검색으로 범위를 조정한다.

PoC 종료 시에는 스키마 정의, 적재·갱신 스크립트, 검색 경로와 주요 Cypher 템플릿, 벡터 인덱스 설정, 근거 연결 규칙, 질의 테스트 사례, 알려진 한계와 재현 방법을 산출물로 남긴다. 설계 상세의 구현 일정·역할은 7장, 보안·개인정보 관리의 구체 절차는 6장, 성능·정확도 검증 기준은 9장에서 확정한다.

## 6. 구현 보완 및 보안·개인정보 보호

### 6.1 기본 원칙과 책임

PoC는 실제 구직자에 대한 채용 결정이나 개인별 취업 가능성 평가를 수행하지 않는다. 공고 검색·비교와 비식별 집계에 필요한 최소 정보만 처리하고, 설문 응답과 인터뷰 자료는 공고 데이터·데모 서비스 계정 정보와 분리한다. 개인정보나 기업 비공개 자료를 다루기 전, 수행기관의 개인정보·보안 담당자와 데이터 이용 조건을 확인하고 처리 목적·접근권한·보관·삭제·사고 대응 책임자를 지정한다. 이 절의 기준은 실행계획이며 법률 자문이나 기관별 의무 검토를 대체하지 않는다.

| 정보 유형 | 예시 | PoC 처리 원칙 |
| --- | --- | --- |
| 공개 채용정보 | 공개 공고 제목·요건·근무지·공고 URL | 출처 이용 조건을 확인하고, 개인 연락처 등 분석에 불필요한 정보는 수집·색인하지 않음 |
| 설문 응답 | 희망 직무·근무조건·급여 범위·역량 자기평가 | 목적에 필요한 항목만 수집하고, 분석용 데이터는 응답자 연락처와 분리 |

### 6.2 동의·고지와 대상자 보호

설문 및 인터뷰 시작 전에 수행 주체, 조사 목적, 수집 항목, 자발적 참여와 중단 방법, 자료 이용 범위, 보관·삭제 계획, 문의처를 이해하기 쉬운 문장으로 안내한다. 참여 동의와 인터뷰 녹음·인용 동의는 목적에 따라 분리하고, 동의하지 않은 응답은 분석에 포함하지 않는다. 동의를 받았더라도 목적에 필요하지 않은 개인식별정보·민감정보·정확한 위치정보는 수집하지 않는다.

PoC 기본안은 모집·동의 절차를 단순화하기 위해 성인 응답자를 대상으로 한다. 미성년자를 포함해야 하는 필요가 생기면 기본 범위에 임의로 포함하지 않고, 법정대리인 동의 등 적용되는 보호 절차와 기관 검토를 완료한 뒤 별도 승인·질문지로 진행한다. 인터뷰 참여와 설문 응답의 연결, 사례비 지급 정보 수집, 녹음·직접 인용은 각각 필요한 범위와 동의 여부를 명시한다.

### 6.3 비식별화·접근통제·보관

설문 연락처와 응답 원자료는 서로 다른 저장 위치·권한으로 분리하고, 연결이 불가피한 경우에는 제한된 담당자만 접근할 수 있는 별도 연결표를 둔다. 분석용 데이터에는 내부 무작위 식별자를 사용하고 직접 식별정보를 제거한다. 직접 식별정보 제거만으로 익명 데이터가 된다고 간주하지 않으며, 지역·직무·연령 등 조합에 따른 재식별 위험도 확인한다. 자유 서술·인터뷰 인용문은 이름·회사·구체 사건 등 식별 가능 요소를 제거하거나 요약·범주화한다.

| 자료 | 접근 권한 | 보관·삭제 제안 |
| --- | --- | --- |
| 참여자 연락처·일정 정보 | 모집·일정 담당자만 접근 | 인터뷰·지급 등 목적이 끝나면 삭제. 실제 삭제 시점은 동의문과 기관 보관 기준에 사전 명시 |
| 설문 원자료·연결표 | 지정된 데이터 책임자만 접근 | 프로젝트 분석에 필요한 기간만 보관. 연결표는 분석용 비식별 자료와 분리하고, 종료 시 삭제 여부를 확인 |
| 비식별 분석 자료·집계표 | 분석 담당자 및 승인된 검토자 | 산출물 재현에 필요한 기간과 이용 조건을 확인해 보관·삭제일 지정 |
| 인터뷰 녹음·전사 | 동의 받은 자료에 한해 지정 담당자만 접근 | 전사 확인 후 원음성 삭제를 기본안으로 검토하고, 전사본도 인용·분석 목적 종료 후 보관 필요성 재검토 |
| 공고 원문·LLM 입력 자료 | 데이터·개발 담당자 | 출처의 이용 조건과 외부 전송 허용 범위에 따르고, 불필요한 복제본·임시 파일 삭제 |

보관 기간은 자료 수집 전에 기관 담당자와 확정해 동의문·출처 대장에 반영한다. 임의로 장기 보관하지 않고, 삭제 예정일에 원본·복제본·임시 저장소·벡터 인덱스·백업의 삭제 또는 비활성화 여부를 점검한다. 백업에서 즉시 개별 삭제가 불가능한 경우에는 해당 제약과 만료 시점을 문서화하고 재적재 시 삭제 대상이 복원되지 않도록 한다.

데모용 결과는 소수 응답자 추정이 가능한 세부 분할을 피한다. 기본 공개 규칙으로 집계 셀의 응답자가 5명 미만이면 수치를 숨기거나 더 큰 범주로 합치되, 모집단·조합에 따른 재식별 위험이 더 크면 기준을 상향하거나 결과를 공개하지 않는다. 그래프 시각화에도 개인 응답자 노드를 만들지 않고, 집계 노드는 분모·기간·정의가 확인되는 경우에만 표시한다.

### 6.4 인프라·계정·비밀정보 보호

- 저장소는 프로젝트 참여자만 접근할 수 있게 하고, 관리자·개발·조회 권한을 구분한다. 외부 데모는 인증 또는 접근 제한을 적용하고 공개 URL에 원자료·관리 콘솔을 노출하지 않는다.
- DB와 API는 최소 권한을 적용한다. 데모 질의 계정은 읽기 전용으로 구성하고, 적재·스키마 변경 계정은 별도 보관·사용한다. 인터넷에 DB 포트를 무방비로 공개하지 않는다.
- API 키·DB 비밀번호는 환경변수 또는 승인된 비밀정보 저장소로 주입하고, `.env`, 자격증명 파일, 데이터 덤프가 버전 관리에 올라가지 않도록 점검한다. 문서·스크린샷·시연 화면에도 비밀값을 표시하지 않는다.
- 전송 구간에는 TLS 등 안전한 연결을 사용하고, 로컬·클라우드 저장소의 접근 권한과 암호화 기능을 확인한다. 데이터 다운로드·복사는 승인된 저장 위치와 기기에서만 수행한다.
- 로그에는 원문 질문·응답·설문 내용 전체를 기본 기록하지 않는다. 오류 분석에 필요한 시간·요청 ID·처리 단계·오류 유형 중심으로 남기고, 불가피한 입력 로그는 개인정보 제거·접근 제한·보관 기간 설정을 적용한다.

### 6.5 외부 LLM·임베딩 서비스 이용 기준

외부 모델에 입력하는 텍스트는 원칙적으로 분석에 필요한 최소 범위로 줄이고, 응답자 개인정보·연락처·참여 식별자·기업 비공개 자료는 전송하지 않는다. 공개 공고라도 출처의 라이선스·약관이 제3자 전송·임베딩·저장을 허용하는지 별도로 확인한다. 제공자의 데이터 보관·학습 사용 정책, 처리 지역, 하위 처리자, API 로그, 삭제 요청 가능성 및 계약 조건을 확인해 승인된 경우에만 사용한다. 조건이 확인되지 않으면 로컬 모델·로컬 임베딩 또는 비식별·요약 데이터로 대체하거나 외부 모델 사용 기능을 제외한다.

LLM 추출 결과는 사실 데이터가 아니라 검수 대상 후보로 취급한다. 구조화 출력 스키마·자료형을 검증하고, 출처 원문에 없는 급여·복지·스킬을 생성했는지 검사한다. 모델의 출력은 HTML·Markdown 등 화면 출력 전에 안전하게 처리하며, 임의의 생성 SQL·Cypher·코드를 실행하지 않는다. 모델이 작성한 답변은 허용된 검색 결과와 대조하고, 근거가 부족하거나 서로 충돌하면 단정 대신 불확실성을 표시한다.

### 6.6 원문 구현안의 보완 사항

기준 원문 예시는 빠른 프로토타입을 위한 참고 코드로 보고, 그대로 운영에 적용하지 않는다. PoC 구현에서 다음 항목을 보완한다.

| 원문 구현상 위험·한계 | 보완 기준 |
| --- | --- |
| 급여 미기재 시 임의의 `3500` 기본값 지정 | 급여는 선택값·결측 사유를 표현하는 스키마로 변경하고 임의 대체값을 제거 |
| 코드 내 API 키·DB 비밀번호 예시 | 실제 비밀값을 코드에 넣지 않고 환경변수·비밀정보 저장소 사용, 예시 값도 저장소에 커밋하지 않음 |
| Text2Cypher에서 위험 요청 허용 옵션 사용 | 운영 DB에서 비활성화하고, 읽기 전용 계정·템플릿 우선·허용 목록·구문 및 결과 검증 적용 |
| 자연어 질문을 생성 쿼리로 직접 실행 | 입력 검증, 읽기 쿼리 제한, 타임아웃·행 수 제한, 위험 작업 차단을 통과한 경우에만 실행 |
| 검색 결과만으로 원인·정책 효과를 단정하는 답변 프롬프트 | 관찰 사실·해석 가설·미확인 사항을 구분하고, 인과·효과 주장은 허용하지 않음 |
| 명시적인 출처 연결 없는 생성 답변 | 공고 ID·출처·게시 시점·원문 근거 위치를 결과에 포함하고 인용 누락 시 응답 제한 |
| 예시 기업·급여·통근점수의 실제 정보 오인 | 샘플 데이터는 데모 화면에서 샘플임을 명확히 표시하고 실측 데이터와 저장·표시상 분리 |

### 6.7 보안·개인정보 사고 대응

자료 오발송, 공개 URL 노출, 계정 탈취, 비인가 접근, 외부 모델로의 비허가 데이터 전송 등 의심 사례가 발생하면 관련 기능·계정·토큰을 우선 차단하고 데이터 처리·공유를 중지한다. 접근 로그와 영향 범위를 보존하되 원문을 불필요하게 복제하지 않는다. 프로젝트 책임자와 기관의 개인정보·보안 담당자에게 즉시 보고하고, 사실관계·영향 자료·조치 내역·재발 방지안을 기록한다. 당사자·기관·관계기관 통지는 담당 기관의 절차와 적용되는 요건에 따라 결정하며, 임의로 사고를 은폐하거나 자체적으로 법적 통지 여부를 단정하지 않는다.

### 6.8 구현·운영 점검표

- [ ] 조사 시작 전 안내문·동의 문구·문의처·보관·삭제 계획 승인
- [ ] 대상자 범위와 미성년자 포함 여부 확정; 별도 보호 절차가 없으면 성인으로 제한
- [ ] 출처별 재사용·외부 전송·임베딩·표시 허용 조건 확인
- [ ] 연락처·연결표와 설문·인터뷰 분석 자료의 저장 위치 및 권한 분리
- [ ] 집계표·그래프의 소수 셀 억제 및 재식별 위험 점검
- [ ] Neo4j 조회 계정 읽기 전용, Text2Cypher 쓰기·관리 명령 차단 및 쿼리 제한 확인
- [ ] API 키·DB 자격증명 저장소 제외, 로그·오류·화면에 비밀정보 미노출 확인
- [ ] 외부 LLM·임베딩에 전송되는 데이터 범위와 제공자 정책 승인
- [ ] 삭제 시 원본·정제본·벡터 청크·임시 파일·백업 처리 계획 확인
- [ ] 사고 연락망·차단·보고 절차 확인 및 데모 접근 제한 점검

이 장의 체크 항목은 실제 수집·외부 서비스 연결·시연 전에 책임자가 확인하고 승인 상태를 기록한다. 기관 정책이나 자료 이용 조건이 충족되지 않으면 해당 데이터 또는 기능을 PoC 범위에서 제외한다.

## 7. 15일 개발 일정과 역할

### 7.1 일정 가정과 운영 방식

아래 일정은 **15영업일 기준의 기본 계획안**이다. 주말·공휴일을 포함한 15일 일정으로 운영해야 하는 경우에는 조사 모집, 데이터 이용 승인, 인력 투입 가능 시간을 다시 확인하고 범위를 조정한다. 작업은 데이터 이용 근거·보안 검토에 의존하므로, 승인이 필요한 자료나 서비스 연결을 확정하기 전에 수집·외부 전송을 시작하지 않는다.

매일 짧은 진행 점검에서 전일 완료·당일 목표·차단 이슈를 확인하고, 결정 사항·범위 변경·미해결 위험은 작업 기록에 남긴다. 데이터 확보량이나 설문 응답 수가 목표에 미달하면 사실대로 기록하고, 기능을 우선 완성하거나 분석 범위를 축소한다. 일정 맞추기를 위해 이용 조건·동의·품질 게이트를 생략하지 않는다.

| QA·검증 담당 | 테스트 질의, 회귀·통합·안전성 검증, 결함 추적 | 테스트 결과표, 미해결 결함 목록 |

인력이 제한된 경우 역할을 겸임할 수 있지만, 데이터 이용·개인정보·외부 서비스 승인과 그에 따른 구현·운영 확인을 가능한 한 한 사람에게만 집중하지 않는다. 겸임자·검토자·최종 승인자를 Day 1에 정하고, 이해관계가 있는 판단은 별도 담당자의 확인을 받는다.

### 7.4 의존 관계와 일정 조정 규칙

- **선행 조건:** 자료 수집과 설문은 출처 이용 조건·동의·보관 기준 확인 후 시작한다. 외부 LLM·임베딩은 데이터 전송 허용 여부를 확인한 뒤 연결한다.
- **핵심 경로:** 권역·데이터 확정 → 정제·품질 검토 → 그래프·벡터 적재 → 근거 포함 질의응답 → UI 통합 → 검증·시연 순으로 진행한다.
- **Day 2 범위 게이트:** 500건 확보 전망이 낮으면 출처·기간을 재검토하고, 승인된 축소 목표(예: 200건 이상 탐색형 PoC) 또는 기능 데모로 분류한다.
- **Day 4 데이터 게이트:** 이용 조건·출처 연결·핵심 필드 품질이 확보되지 않으면 해당 자료·필드를 적재하지 않고, 기능 데모와 데이터 분석 성과를 구분한다.
- **Day 9 기술 게이트:** 검색 근거 연결·수치 재현·안전한 쿼리 실행이 확인되지 않은 기능은 자유 질의로 공개하지 않고 템플릿·필터 기반 기능으로 대체한다.
- **Day 13 통합 게이트:** 오류가 남으면 시연 핵심 흐름을 3~5개 사전 검증 질의로 축소하고, 미완료 기능을 결과물·발표에서 명확히 밝힌다.
- **범위 변경:** 신규 권역·직무·모델·외부 서비스 추가는 기존 검증·보안 작업을 밀어내지 않는 경우에만 승인하며, 변경 사유·영향·승인자를 기록한다.

이 일정은 목표 계획이며 완료 성과를 보장하지 않는다. 실제 종료 보고에는 각 일자별 계획 대비 완료·미완료, 범위 변경, 데이터 확보량, 품질 게이트 결과, 다음 단계의 선행 조건을 기록한다.

## 8. 예산 및 자원 계획

### 8.1 예산 산정 가정

아래 금액은 제안서 작성과 착수 의사결정을 위한 **계획 가정**이며, 확정 견적·시장 단가·실제 집행액이 아니다. 단가는 내부 인건비 기준 또는 외주 견적에 따라 달라질 수 있으므로 Day 1~2에 실제 인력 투입 방식, 기존 보유 자원, 구매·계약·간접비·세금 적용 여부를 확인해 수정한다. 외부 서비스 가격은 사용량·환율·요금제·보관 정책에 따라 달라지므로 계약 전 제공자 견적을 확인한다.

- 종료 시 항목별 계획액·승인액·실제 집행액·차이를 기록하고, 미사용 계정·자원·사례비 예산의 처리 방법을 정산한다.

이 장의 금액과 자원 수는 모두 계획 가정이다. 최종 예산표에는 실제 확보 견적과 승인 금액을 반영하고, 비현금 인력 투입, 직접 경비, 예비비, 세금·간접비를 구분해 기록한다.

## 9. 검증 설계와 완료 기준

### 9.1 검증 목적과 원칙

검증은 제한된 PoC 데이터에서 시스템이 의도한 검색·집계·근거 표시를 수행하는지 확인하는 **기술·데이터 품질 검증**이다. 청년 취업률, 기업 채용 성과, 청년 유출 원인 또는 정책 효과를 입증하는 평가가 아니다. 계획된 기준은 실제 검증 결과가 아니며, 데이터 규모·팀 역량·시연 환경을 확인해 Day 2~4에 확정한다. 시험 결과는 통과율·오류 사례·표본·시험 조건을 함께 기록하고, 기준에 미달한 기능은 범위를 축소하거나 미완료로 표시한다.

### 9.2 검증 데이터와 테스트 질문 구성

질의응답 평가에는 실제 데이터와 분리된 테스트 질문 목록을 사용한다. 시스템 구현 담당자만 질문을 정하지 않도록 도메인 검토자를 포함하고, 예상 답·필요 출처 ID·산식·기대 동작(답변, 부분 응답, 보류)을 질문별로 사전에 기록한다. 응답 생성 프롬프트 조정에 사용한 질문과 최종 평가용 질문은 가능한 한 분리하고, 최종 평가 질문은 조정 과정에서 반복 노출하지 않는다.

| 서술 근거 검색 | 업무·자격·복지 설명 구절 찾기 | 원문 청크·출처·게시 시점 |
| 비교·설명 | 공고 조건과 선호 집계의 탐색적 비교 | 비교 가능한 범주, 각 자료의 분모와 기간, 한계 |
| 근거 부족·범위 밖 | 자료에 없는 급여·원인·정책 효과 질문 | 추측하지 않고 미확인·범위 제한·응답 보류 |
| 안전성 | 쓰기 쿼리, 프롬프트 인젝션, 비허가 데이터 요청 | 쿼리 차단, 권한 거부, 민감정보 미노출 |

초기 계획으로 총 20~30개 질문을 구성하고, 각 유형에 여러 사례를 배치한다. 이는 PoC 테스트 커버리지를 위한 운영 목표일 뿐 통계적 평가 표본이 아니다. 핵심 시연 질문은 별도로 사전 검증하고, 테스트 질문·기대 결과·사용한 데이터 버전·판정자를 함께 보존한다.

### 9.3 검증 항목과 제안 기준

아래 수치는 **제안된 PoC 통과 기준**이며, 결과를 미리 의미하지 않는다. 평가 전에 테스트 세트와 기준을 고정하고, 기준 변경 시 변경 이유·시점·승인자를 기록한다.

| 영역 | 측정 방법 | 제안 완료 기준 |
| --- | --- | --- |
| 데이터 적재·스키마 | 원천·정제 건수 대조, 중복·필수 필드·관계 적재 검증 | 적재 건수·제외 건수 재현 가능, 출처 ID 연결 및 주요 필드 검증 완료 |
| 구조화 검색 | 사전 정의 질의 결과를 검수된 기준 목록·집계와 비교 | 필수 시연 질의의 결과와 필터 조건이 기대와 일치하고, 집계는 독립 재계산과 일치 |
| 수치 재현성 | 동일 데이터 버전·조건에서 건수·분모·급여 산식 재실행 | 핵심 시연 수치 100% 재현, 단위·결측 처리·분모 표시 |
| 벡터 검색 | 상위 검색 결과의 관련성·출처·원문 위치를 사람이 판정 | 핵심 질문의 상위 5개 결과 중 관련 근거 비율 80% 이상을 목표로 검토 |
| 출처·인용 완전성 | 사실 주장별 지원 출처와 표시된 출처 대조 | 핵심 시연의 수치·사실 주장 모두 근거 연결. 인용 없는 사실 주장은 배포 전 수정·제거 |
| 답변 근거성 | 답변을 근거 자료와 대조해 지지·부분 지지·미지지 분류 | 핵심 시연 질문에서 미지지 사실 주장 0건을 목표로 하고, 미해결이면 해당 답변 기능을 제한 |
| 안전한 응답 | 근거 부족·범위 밖·쓰기 요청·인젝션 질문 시험 | 비허가 쓰기·관리 작업 실행 0건, 근거 없는 수치·인과 단정 0건을 목표로 함 |
| 개인정보·보안 | 접근권한, 로그, 외부 전송, 출력·시각화 점검 | 승인되지 않은 개인자료 노출·외부 전송 0건, 비밀정보 노출 0건 |
| 사용성·응답시간 | 5~10개 대표 질의를 동일 데모 환경에서 반복 측정, 내부 검토자 사용 확인 | 시연 핵심 경로 완료 가능, 응답시간 중앙값과 최대값을 기록하고 지연 오류를 수정 또는 고지 |

`상위 5개 결과 중 관련 근거 비율`은 사람이 판정한 소규모 내부 지표로만 보고한다. 검색 결과가 5개 미만인 질의는 실제 반환된 결과 수를 분모로 삼고, 결과 수·테스트 질문 수와 판정 기준을 공개한다. 표본이 작으므로 이 비율을 일반적인 검색 정확도 보장으로 표현하지 않는다. 응답시간도 특정 장비·네트워크·모델·데이터 버전의 관찰값으로 기록하며 서비스 수준 보장으로 확대하지 않는다.

### 9.4 수동 평가 절차

1. 평가 대상 데이터·그래프·벡터 인덱스·모델·프롬프트 버전을 고정한다.
2. 질문별 예상 답변의 핵심 항목과 근거 출처·계산식을 검토자가 미리 작성한다.
3. 질의를 실행해 생성 Cypher(해당 시), 검색 결과, 출처, 계산값, 최종 답변, 응답시간을 보존한다.
4. 검토자가 답변의 사실 주장·인용·분모·한계를 `지지`, `부분 지지`, `미지지`, `판정 불가`로 분류한다.
5. 오류를 데이터 오류, 검색 누락, 쿼리 오류, 계산 오류, 답변 생성 오류, 인용 오류, 범위 초과로 분류해 원인과 수정 조치를 기록한다.
6. 수정 후 전체 핵심 평가 세트를 재실행해 회귀 여부를 확인한다. 평가 질문을 수정·삭제할 때에는 이유를 기록한다.

고위험 또는 해석이 필요한 결과는 한 명의 작성자만으로 통과 처리하지 않는다. 가능한 범위에서 구현자와 독립 검토자가 나누어 판정하고, 판정이 다르면 합의 또는 판정 불가로 남긴다. 평가 결과에 유리한 사례만 골라 보고하지 않는다.

| 구분 | 완료 기준 |
| --- | --- |
| 데이터 준비 | 이용 조건이 확인된 데이터만 사용하고, 출처·버전·결측·제외·중복 기록과 품질 보고서를 보유 |

공고 확보량이 축소 기준에 미달하거나 청년 설문 데이터가 확보되지 않은 경우에도 기능 시연은 가능할 수 있으나, 데이터 분석 완료로 보고하지 않는다. 분석 기준을 충족하지 못하면 해당 지표를 삭제·축소하고 기능 PoC와 분석 PoC의 결과를 분리한다. 심각한 보안·개인정보 문제, 출처를 확인할 수 없는 데이터, 재현 불가능한 핵심 수치가 남으면 외부 시연·배포를 보류한다.

### 9.6 검증 산출물과 보고 양식

최종 검증 패키지에는 테스트 질문·기대 근거, 기준 데이터 버전, 검색·계산·답변 결과, 오류 및 수정 이력, 보안 점검 기록, 완료·미완료 기준표를 포함한다. 보고서의 각 정량 결과에는 다음 메타정보를 붙인다.

- 지표 정의와 계산식, 테스트 대상 수와 분모
- 데이터 출처·수집 기간·버전, 포함·제외·결측 처리
- 테스트 환경·모델·프롬프트·색인 설정
- 통과 수·실패 수·판정 불가 수, 대표 오류와 수정 여부
- 표본·모집·자기보고·시점 차이 등 해석 한계

완료 보고에는 “계획 목표”, “실제 확보·구현 결과”, “검증 결과”, “후속 실증 필요사항”을 분리해 쓴다. 이 PoC의 통과는 제한된 데이터와 조건에서 기술적 실행 가능성을 확인했다는 의미이며, 서비스의 일반적 정확성이나 노동시장·정책 효과를 입증하는 것으로 해석하지 않는다.

## 10. 시연·보고 및 실증 확장

### 10.1 시연의 목적과 사전 조건

시연은 제한된 PoC 데이터에서 사용자가 공고 조건을 검색하고, 관련 근거와 표본 범위를 확인할 수 있는 흐름을 보여주는 기술 데모다. 청년 유출 원인을 밝혀냈거나 특정 정책의 효과를 입증하는 발표로 구성하지 않는다. 발표 화면·대본·보고서의 수치와 기업·지역 사례는 실제 사용이 승인된 자료인지 확인하고, 실측 결과·계획 목표·샘플 데이터를 시각적으로 구분한다.

시연 전에는 테스트 환경에서 대표 질의를 반복 실행해 검색 근거·출처 링크·계산값·응답시간·오류 처리를 확인한다. 실제 출처 연결 또는 보안 점검에 실패한 기능은 시연에서 제외한다. 설문 응답과 인터뷰 인용은 동의·비식별·소수 집단 공개 기준을 통과한 집계 결과만 사용한다. 샘플 데이터가 필요한 경우 화면에 **“설명용 샘플 데이터—실측 결과 아님”**을 계속 표시하고 실제 통계와 혼합하지 않는다.

### 10.2 3분 시연 시나리오

아래는 선정 권역·직무군과 실제 데이터에 맞춰 바꿔 사용할 수 있는 진행안이다. 대괄호는 시연 전에 확인된 값으로 채우며, 출처가 없는 숫자나 원인 해석은 입력하지 않는다.

| 경과 시간 | 화면·진행 | 전달 내용 |
| --- | --- | --- |
| 0:00~0:30 | 시작 화면에서 분석 권역·직무군·기간·자료 수 표시 | “이 데모는 [권역·직무군]의 [기간] 자료를 대상으로 한 제한된 기술 PoC이며, 부울경 전체를 대표하거나 정책 효과를 검증하는 결과는 아닙니다.” |
| 0:30~1:10 | 질문 입력 또는 준비된 필터 선택 | “이 범위에서 [직무군] 공고의 요구 역량과 근무 조건을 확인해 보겠습니다.” 질문은 데이터가 실제로 답할 수 있는 범위로 한정 |
| 1:10~1:50 | 공고 검색·그래프 관계 시각화 | 공고와 직무·스킬·지역의 연결을 보여주고, 한 공고를 열어 원문 출처·게시 시점·검수 상태 확인 |
| 1:50~2:30 | 구조화 집계 또는 공고 설명 검색 | 확인 가능한 표본 수·분모·결측 안내와 관련 원문 근거를 함께 표시. 검색되지 않은 정보는 미확인으로 안내 |
| 2:30~3:00 | 한계·후속 질문 제시 | “관찰된 차이는 후속 검증이 필요한 가설입니다. 표본·모집·공고 기재 한계를 고려해 다음 실증에서 확인할 질문을 제안합니다.” |

### 10.3 사전 검증 질문과 데모 준비물

질문 목록은 실제로 수집된 데이터의 범위에 맞춰 확정한다. 아래는 질문 형식 예시이며, 답변 내용이나 수치는 미리 정해진 실측 결과가 아니다.

1. **공고 찾기:** “[선정 권역]에서 [직무군]에 해당하고 신입 지원이 가능한 공고를 보여줘.”
2. **요구 역량:** “현재 자료에서 해당 직무 공고에 명시된 필수 스킬과 우대 스킬은 각각 무엇인가?”
3. **근무 조건:** “공고에 명시된 원격·유연근무·통근·주거 관련 조건은 무엇이며, 원문 출처는 어디인가?”
4. **집계·결측:** “급여가 명시된 공고의 수와 급여 단위·범위는 무엇이며, 급여 미기재 공고는 몇 건인가?”
5. **응답 보류:** “이 조건 차이가 청년 유출의 원인이라고 결론 내릴 수 있는가?” → 관찰 자료만으로 인과 결론을 낼 수 없다고 안내.

시연 준비물은 고정된 테스트 데이터 버전, 시연 계정·접근 권한, 대표 질의와 기대 근거 목록, 출처 확인용 공고 원문, 정상·빈 결과 화면, 시스템 장애 시 사용할 사전 녹화 또는 캡처 자료, 발표 대본, 질문 대응표다. 백업 화면은 현재 시스템 화면으로 오인되지 않도록 녹화·정적 자료임을 표시한다. 데모 중 실시간으로 공고를 추가 수집하거나, 승인되지 않은 계정·DB를 연결하지 않는다.

| 계획 대비 실적 | 공고·설문·인터뷰 목표와 실제 확보·유효·제외 건수, 일정·예산 변경 |
| 데이터 품질 | 출처별 구성, 이용 조건, 중복·결측·검수·정규화 결과와 미확인 필드 |
| 구현·검증 결과 | 기능별 테스트, 질의·근거·수치 재현 결과, 오류·보안·성능 제한 |
| 탐색적 관찰 | 조건별로 관찰된 차이, 비교 기준·분모·표본 수·불확실성, 인과 해석 제외 |
| 제한·위험 | 표본 편중, 공고의 기재 한계, 조사 자기보고·시점 차이, 시스템·라이선스 위험 |
| 후속 제안 | 다음 단계의 검증 질문, 추가 데이터·표본·기간·협력·예산·승인 조건 |

결론에서는 “기술적으로 동작했다”, “특정 데이터 범위에서 관찰됐다”, “추가로 검증할 필요가 있다”를 구분한다. 취업률 향상, 인력 유출 방지, 정책 효과처럼 측정하지 않은 성과를 PoC 성과로 표현하지 않는다. 인용 가능한 결과는 근거 공고·집계 정의·테스트 결과와 연결하고, 샘플·가정 값은 실측 자료와 분리한다.

### 10.5 이해관계자별 전달

| 대상 | 전달 초점 | 전달 시 주의 |
| --- | --- | --- |
| 청년 구직자 | 공고 조건·근거 확인, 미기재 정보와 개인 선호의 구분 | 적합도 점수나 취업 가능성 예측으로 오인되지 않도록 안내 |
| 기업·산단 담당자 | 공고 기재 내용·요구 역량·근무 조건의 탐색적 비교 | 표본·직무·기간을 벗어난 기업 평가나 인과 해석을 금지 |
| 지자체·대학·취업기관 | 데이터 공백, 조사 설계, 후속 실증에서 확인할 질문 | 기술 데모를 정책 효과 증거나 전체 청년의 대표 의견으로 사용하지 않음 |
| 개발·운영 담당자 | 재현 절차, 품질·보안 결과, 비용·운영 의존성, 미완료 항목 | API 키·개인정보·비공개 원문이 포함된 화면·로그를 공유하지 않음 |

외부 공개 자료는 개인정보·재식별 위험·출처 이용 조건·기업 비공개 정보를 재검토하고, 승인된 요약·집계만 포함한다. 원자료·연락처·개별 인터뷰 기록은 발표 자료나 데모에 제공하지 않는다.

### 10.6 후속 실증 확장 단계

15일 PoC 후 사업 확대를 자동 결정하지 않는다. 아래 단계는 후속 검토의 계획안이며, 기간·표본·예산은 파트너십과 데이터 확보 가능성에 따라 다시 산정한다.

| 단계 | 목표·주요 작업 | 다음 단계 진입 조건 |
| --- | --- | --- |
| A. 기술 PoC (15영업일) | 제한된 권역·직무와 데이터로 수집·검색·출처 제시·검증 가능성 확인 | 이용 조건·보안·기술 검증 결과 및 미완료 사항 보고 |
| B. 제한 실증 (계획상 약 8~12주 검토) | 복수 출처 자료의 이용 승인, 직무·권역 분류 보강, 조사 표집·질문지 개선, 사용자 테스트, 데이터 갱신·품질 절차 검증 | 참여기관·데이터 제공 협약, 조사 설계·표본 계획, 개인정보·보안 승인, 실증 예산·평가 계획 확보 |
| C. 운영형 서비스 검토 | 보안·권한·장애 대응·모니터링·갱신 SLA, 사용자 지원, 장기 비용·유지보수 구조 평가 | 운영 주체·책임·재원·서비스 수준·법률 및 보안 검토 완료 |
| D. 정책·성과 평가 연구 | 사전에 정한 성과 지표와 비교 설계로 개입의 효과를 평가 | 충분한 기간·표본·비교집단 또는 적절한 준실험 설계, 데이터 접근 및 독립 평가 계획 확보 |

제한 실증에서는 청년 응답을 더 대표성 있게 수집할 수 있도록 모집단·표본틀·층화 기준·응답률을 사전에 설계하고, 권역·직무·경력·성별 등 비교 범주를 분석 전에 정한다. 공고 자료는 장기적으로 중복·삭제·갱신 이력을 관리하고, 출처별 이용 조건과 기업 정보의 최신성을 정기 검토한다. 정책 효과를 평가하려면 단순 전후 비교만으로 인과를 단정하지 말고, 적절한 비교집단·기준선·관찰 기간·교란 요인 통제 가능성을 평가 설계에서 검토한다.

### 10.7 후속 의사결정 질문

PoC 종료 회의에서 다음 질문에 답하고, 근거·담당자·기한을 기록한 뒤 확장 여부를 결정한다.

- 공고 데이터의 이용·갱신·재배포 조건이 장기 실증에도 유효한가?
- 현재 확보한 데이터로 비교하고자 하는 권역·직무·경력 조건을 맞출 수 있는가?
- 청년 조사 모집 경로와 표본 계획이 의사결정에 필요한 집단을 포함하는가?
- 외부 LLM·클라우드·벡터 검색을 계속 사용할 보안·비용·계약 근거가 있는가?
- 기관·기업·대학·청년 참여 주체의 역할, 결과 이용 범위, 책임과 운영비가 합의되었는가?
- 제안하려는 후속 정책 가설을 평가할 기준선·비교 설계·성과 지표·기간이 준비되었는가?

조건이 충족되지 않으면 자동 확장하지 않고, 데이터 추가 확보·질문지 개선·기능 축소·실증 보류 중 적절한 조치를 결정한다.

승인되지 않은 항목은 ‘진행 중’으로 표시하고, 해당 항목에 의존하는 수집·연결·공개 기능은 시작하지 않는다. 체크리스트에는 담당자 이름 또는 역할, 확인 날짜, 증거 자료 위치, 예외 승인자를 기록한다.

### 11.4 위험 발생 시 의사결정·보고

위험이 발생하면 작업자는 즉시 영향받는 데이터·기능·외부 공개를 식별하고, 심각한 정보 노출·비허가 처리·잘못된 결과 확산 위험이 있으면 우선 중지한다. 책임자는 사실 확인, 영향 범위, 필요한 보고·승인, 대체 일정·기능, 재개 조건을 결정 로그에 남긴다. 외부 공개물의 오류는 조용히 덮어쓰지 않고 정정 이력과 재배포 여부를 기록한다.

최종 종료 회의에서 위험별 상태를 종료·수용·후속 이관으로 구분한다. 수용한 위험에는 근거·잔여 영향·책임자를 기록하며, 개인정보·데이터 이용 권한·보안상 중대한 위험은 단순히 일정 사유로 수용하지 않는다.

## 12. 원문 대비 보완사항 및 최종 점검

### 12.1 기준 원문 대비 주요 보완사항

기준 원문은 빠른 기술 데모를 위한 아이디어·샘플 구현으로 활용하고, 계획서는 실제 수집·검증 전의 불확실성, 이용 조건, 품질·보안·평가 절차를 추가했다. 원문에서 사용한 예시나 권고 수치는 실측 결과 또는 확정된 사업 조건으로 전환하지 않았다.

| 항목 | 기준 원문의 내용·한계 | 종합계획서의 보완·적용 방식 |
| --- | --- | --- |
| 목표·해석 | 청년 유출 원인과 정책 제언까지 분석하는 것으로 표현 | 15일 PoC는 데이터·검색·근거 제시의 기술 타당성 검증으로 한정. 인과·취업 성과·정책 효과는 후속 실증으로 분리 |
| 지역·데이터 범위 | 핵심 거점 1~2곳, 공고 500~1,000건 제안 | Day 1에 권역 1곳·직무군 1~2개를 확정하고, 500건을 운영 목표로 설정. Day 2에 확보 전망 검토 후 조건부 축소·재분류 |
| 표본 대표성 | 공고·설문을 통해 부울경 전체의 미스매칭을 진단하는 인상을 줄 수 있음 | 단기 설문 30~50명과 인터뷰 5~8명은 계획 목표로만 사용. 편의 표본·자기보고·모집 편중을 명시하고 전체 청년으로 일반화하지 않음 |

| 일정·예산·자원 | 15일 스프린트와 특정 기술 조합을 전제로 서술 | 15영업일 계획안과 역할·의존성·게이트를 제시하고, 인력·예산·직접 경비 수치는 계획 가정·견적 확인 대상으로 명시 |

### 12.4 최종 운영 원칙
